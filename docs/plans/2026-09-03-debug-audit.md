# Debug audit — multi-angle defect hunt

Date: 2026-09-03
Commit audited: 49db942 (`main`, the 0.7.4 release commit)
Status: findings only. Nothing in this document has been fixed; every item below is a proposal until a failing test pins it.

This is a hunt, not a review. Eight independent passes went over the code from eight angles, each one required to reproduce what it claimed before writing it down. What follows is the merged, de-duplicated result, ordered by what it would cost to leave alone, plus the plan for working it off.

## How to read this

**Severity** answers "what happens if we ship without fixing it":

- **Critical** — a published artifact or a user's profile can be made wrong or unsafe by someone we do not control (an npm author, a CDN, a client message). Fix before the next release.
- **High** — wrong behaviour on inputs that exist in the live ecosystem today, or a spec invariant from CLAUDE.md that the code does not actually hold. Fix in the next release.
- **Medium** — wrong behaviour on inputs that are plausible but not yet observed, or a robustness gap that turns an outage into a bad publish. Schedule.
- **Low** — a gap the tests should close, or a hardening that costs little. Batch.

**Confidence**: *Confirmed* means the auditor reproduced it with a script or a targeted test and the command is quoted. *Plausible* means it was reasoned from the code and not run; treat those as hypotheses and reproduce them first — the plan below puts a failing test in front of every fix for exactly that reason.

**Angles** (the letter prefix on each finding id):

| | Angle | What it asked |
|---|---|---|
| A | Hostile npm input | Where does attacker-controlled text end up, and is it validated or escaped at that boundary? |
| B | Policy correctness | Does the gate decide listing, tier and reason exactly as the spec says, for every edge case? |
| C | Determinism and purity | Same inputs, byte-identical artifacts, regardless of clock, order, locale or machine? |
| D | Network shell | Does the impure layer survive timeouts, 429s, partial responses, eventual consistency, budget exhaustion? |
| E | Config, I/O, CI, supply chain | YAML coercion, atomic writes, workflow races, pinned actions, secrets. |
| F | Host process layer | Spawning, tar, npmrc, concurrency, restarts, hot-load, the compatibility check, Windows. |
| G | RPC, catalog loading, client | Boundary validation, integrity of the fetched catalog, i18n interpolation, XSS surface, state races. |
| H | The test suite itself | Tests that pass for the wrong reason, fixtures whose arithmetic is false, properties claimed but not established. |

### 1. A name is not an identity

The registry's uniqueness rule is `npm:<name>` for npm entries and `github:<repo>#<subdir>` for GitHub entries (`registry/scripts/src/emit.ts:107-109`). Reviews, denials, the similarity hold, first-seen dates, the sort comparators, the RPC methods and the client's lookup maps all key on the bare `name`. Every finding in this section is that mismatch surfacing somewhere.

**[G-1] High | Confirmed | `packages/dsh-plugin-shop/src/host/install.ts:25-29`, `src/host/index.ts:637,862` and `installed()`, `src/client/ShopTab.tsx:714,872-878`.** `installStart {name, version}`, `validateInstall` (`.find` by name), `installed()` (one row per same-named catalog entry) and the client's `installedByName`/`tiers`/`sources` maps address entries by name. With `alice/dsh-foo@A` and `bob/dsh-foo@B` in the catalog and bob's installed, `installed()` returns two rows for one plugin, one of them `outdated: true`; the Outdated row's Update button spawns `plugin add github:alice/dsh-foo#aaaa…`, replacing the user's plugin with another repository's commit, gated on the other entry's tier; installing bob's again fails with `version-mismatch: dsh-foo@bbbb… is not the cataloged version (aaaa…)`, a published detail that is false. `<li key={row.name}>` also duplicates React keys. `present.ts:286` records that the live catalog has 151 such names over 243 entries. Fix: address entries by `(source, name, repo, subdir)` end to end; `installed()` should match the manifest's `github:owner/slug` spec to `entry.repo`. Test first: a fixture catalog with two same-named GitHub entries, one installed; assert one row, `outdated: false`, and that `installStart` for the installed identity spawns that identity.

**[A-2] High | Confirmed | `registry/scripts/src/gate.ts:132`, `pipeline.ts:51-55`.** The npm gate treats `distance === 0` to a verified name as "same identity" and skips the hold; `runPipeline` then marks the repo `shadowed-by-npm`. Nothing checks that the npm package is the same project. With `dsh-x` verified by `reviewedCommit` and `allowed-similar: good/dsh-x`, publishing `dsh-x` on npm turns the shelf from `github:good/dsh-x tier=verified added=2026-08-01` into `npm:dsh-x tier=community added=2026-08-01 publisher=evil`. Fix: an npm candidate whose exact name is verified with a `reviewedCommit`/`reviewedSha256` pin is a different identity; hold it (`name-too-similar`, edits 0) unless cleared; key first-seen for repo entries by `owner/slug`. Test first: the fixture above, asserting the npm candidate is held and the GitHub entry stays listed.

**[B-2] High | Confirmed | `registry/scripts/src/repo-gate.ts:111-125`.** The repo-channel hold treats `edits === 0` on the slug or bundle name as the most dangerous lookalike. A `verified.yml` row `name: dsh-repo-plugin, reviewedCommit: <sha>` therefore rejects the very repository the human reviewed with "Exactly matches the verified package dsh-repo-plugin; only an explicitly allowed source may use that name", and the pipeline lists nothing. Root cause: a GitHub review has no repo binding, so the gate cannot tell the reviewed repo from a namesake. No test drives a `reviewedCommit` review through `gateRepo`. Fix: record `repo:` on GitHub reviews and exempt that identity from the hold. Test first: a pipeline test with one `reviewedCommit` review and the reviewed repo as the only candidate, asserting it is listed `verified`.

**[B-3 / A-4] High | Confirmed | `registry/scripts/src/tier.ts:72-104` (`assignRepoTier`), `repo-gate.ts:111`.** The only exit from B-2 is `allowed-similar.yml`, whose unit is a name. Clearing the name clears every repository using that bundle name, and `assignRepoTier` looks the review up by bundle name alone: `bob/dsh-repo-plugin` at a commit nobody reviewed lists as `verified-stale` with `reviewer: github:alice-reviewer`, and at the reviewed commit as `verified`, skipping the acknowledgement. 83 live bundle names are already claimed by both a fork and an original. Fix: key GitHub reviews by `(repo, commit)`; for repo candidates honour only the `owner/slug` form of `allowed-similar`. Test first: original and fork with the same bundle name, one review; assert the fork is `community` with no `review` attached.

**[B-6] Medium | Confirmed | `registry/scripts/src/pipeline.ts:51-55`, `gate.ts:71`.** Denying `evil/dsh-x` does nothing once the author publishes `dsh-x` to npm from that repository: the npm gate checks only the name, npm wins, the repo is reported `shadowed-by-npm` instead of `denied`, and the catalog's `denied[]`, which the Host's install gate consults, is empty. Fix: check `githubOwnerName(candidate.repository)` against repo denials in the npm gate, case-folded, and run the denial check before the shadow short-circuit. Test first: the fixture above, asserting `denied[]` carries the row and nothing is listed.

**[C-2] Medium | Confirmed | `registry/scripts/src/emit.ts:155,163,174,179`.** The sorts key on `name` only; ties keep input order. 172 bundle names / 451 entries in the live catalog are claimed by several repositories (`dsh-skill-manager` by 14). Reversing `repoCandidates` changes the `plugins.<sha>.json` hash, `manifest.lock` and `index.json`. Masked today because `github-client.ts` feeds candidates in repo-sorted order; `pipeline.test.ts:81-88` reverses npm candidates only. Fix: sort entries, lock lines and rejections by the full identity. Test first: extend the determinism test to reverse repo candidates and assert all artifacts identical.

**[C-6 / B-10 / A-8] Low | Confirmed | `registry/scripts/src/pipeline.ts:51-55`.** `shadowed-by-npm` rows name `owner/slug`, not the `owner/slug#subdir` unit that `repo-gate.ts` and the design use, so a monorepo with several shadowed subpackages emits identical rows and their order follows input. Fix: build the same `unit` string; sort rejections by `(name, code, detail)`.

**[B-9] Low | Confirmed | `registry/scripts/src/build.ts:212-216`.** `added` is stamped for every harvested candidate before the gate, while the backfill used the first listed snapshot and `types.ts` defines the field as first appearance in the catalog. A package rejected for weeks and then listed carries its first-harvest date. Fix: record first-seen from accepted entries.

### 2. The daily write-back loop

The build writes four files back into the repository and a bot commits them. Three things are wrong with that loop, and two of them interact.

**[C-1 / A-6 / E-1] High | Confirmed | `.github/workflows/daily.yml:133`, `registry/scripts/src/build.ts:212,235`.** The snapshot step runs `git add registry/snapshots/manifest.lock registry/repo-state.json`. `first-seen.yml` is written at `build.ts:235` and never added; `git log -- registry/first-seen.yml` shows two commits, both the 2026-08-31 backfill. Every name absent from the committed file is stamped `builtAt.slice(0, 10)` at `build.ts:212`, so it is "first seen today" again tomorrow. Live 2026-09-03 catalog: 4,842 of 9,422 entries carry `added: "2026-09-03"`; between the 09-02 and 09-03 builds 3,197 entries differ only in `added`. The content hash therefore changes daily for packages whose content did not, `publish-catalog.ts`'s "unchanged, skip" path can never fire (six `dsh-plugin-shop-catalog` versions were published on 2026-09-03), and `added` is fiction for half the shelf. This is the `builtAt` invariant broken through a side door. Fix: add `registry/first-seen.yml` to the snapshot `git add`; re-run `backfill-first-seen.ts` once (the daily `manifest.lock` history makes the real dates recoverable). Test first: a test that every file `build.ts` writes under `registry/` is named in the workflow's `git add` line, so the next such file cannot be forgotten. Fix together with A-3, see below.

**[E-2] High | Confirmed | `.github/workflows/daily.yml:64-70,130-136`.** Both bot commits `git push` without fetching or rebasing, under `continue-on-error: true`. Run 33731280504 (schedule, 2026-09-03, conclusion `success`): `! [rejected] main -> main (fetch first)` at 08:24 for the classifier commit and at 08:53 for the snapshot commit; run 33623131511 (2026-09-02, `success`): the same twice. A human push during the roughly 50-minute run makes `main` non-fast-forward even when it does not trigger the workflow. Each occurrence silently discards the day's LLM verdicts and the repo-state backfill memory; on 2026-09-03 the snapshot only landed because a later push-triggered run happened to check out the newer `main`. Fix: `git fetch && git rebase origin/main` with one retry before each push; make the step fail visibly or at least emit `::warning::`. Test first: none possible in vitest; verify by reading the next scheduled run's log for `[rejected]`.

**[A-3 / E-3] High | Confirmed (serialiser) / Plausible (LLM echo) | `registry/scripts/src/categories.ts:36`, `config.ts:188`, `github-client.ts:437`, `build.ts:215`.** Both serialisers emit `- name: "${name}"` unescaped, justified by a comment that npm names never contain `"` or `\`. GitHub manifest names are unrestricted (`repo-state.json` already holds `Skills Manager` and `{{PKG_NAME}}`), `projectCandidate` accepts any non-empty string and `gateRepo` never checks name shape. Probes: `dsh-"quote` parses as `Unexpected scalar at node end`; `dsh-a"\n  category: tool\n- name: "dsh-victim` throws `duplicate entry for dsh-victim`; `dsh-trailing\` parses with the name silently altered; `dsh-b" # comment` parses as `dsh-b` and writes another package's row. `first-seen.yml` receives every repo candidate name, gated or not; `categories.yml` receives it once the LLM echoes it, after which `loadRegistryConfig` throws on every subsequent run until a human edits the file. Fixing C-1 alone makes this trivial to trigger, because committing `first-seen.yml` commits the hostile name. Fix both in one change: `JSON.stringify` the name in both serialisers (as `markets.ts` already does) and validate GitHub manifest names against the npm name grammar at `projectCandidate`, rejecting with their own detail. Test first: round-trip the four probe names through serialise → parse for both files.

**[E-5] Medium-Low | Confirmed | `registry/scripts/src/config.ts:8-25`, `gate.ts:71`, `repo-gate.ts:57`.** `denied`/`verified`/`allowed-similar` names are not shape-checked and are matched exactly: `" dsh-evil "`, `DSH-Evil` and a block scalar `dsh-evil\n` all load and can never equal an npm name, so a mistyped denial fails open with no signal. Nothing reports a denial or review that matched no harvested candidate. Fix: a name regex on every row (npm grammar or `owner/slug`) and a "matched nothing" line in `report.md`.

**[E-12] Low | Confirmed | `registry/scripts/src/config.ts:84-90`.** Loader errors name the row index, not the package (`verified.yml: 2.reviewer Invalid input`); an empty or comments-only file reads `expected a YAML list, got object`; a UTF-8 BOM immediately before `- ` fails as `Unexpected scalar at node end at line 1, column 4`. Fix: include `row.name` when present, special-case `null`, strip a leading BOM.

### 3. Trust and tier semantics

**[B-1] High | Confirmed | `registry/scripts/src/tier.ts:52`, `packages/dsh-plugin-shop/src/host/install.ts:36`.** `gt(candidate.version, review.reviewedVersion)` only downgrades newer versions, so `latest=1.1.0`, `latest=0.0.1` and `latest=1.2.0-rc.9` against `reviewedVersion=1.2.0` all render `verified`. A `latest` older than the review is exactly what a hotfix published without `--tag` produces (the dsh-market incident in `docs/design/2026-08-31-market-borrowings.md` §C-2), and an unpublish does the same. `install.ts:36` skips the acknowledgement only for `verified`, so unreviewed code installs without the warning. The spec's invariant ("verified pins a version, never a name") contradicts its own rule ("if latest exceeds reviewedVersion"); the repo channel already uses exact match (`reviewedCommit !== commit`, `reviewedSha256 ===`); `tier.test.ts:112` pins the weak behaviour. Fix: exact match (`neq`) for npm, like the other two pins; amend §7.1 and the CLAUDE.md bullet in the same change. Test first: the three cases above, asserting `verified-stale`.

**[B-4] High | Confirmed | `registry/scripts/src/gate.ts:129-136`.** The hold compares every candidate against every verified name except its own exact name, so verifying `dsh-tool-a` and `dsh-tool-b` (distance 1, the shape of a same-author suite) removes both from the catalog, each "Within 1 edit(s) of the verified package" the other. A review is already the adjudication the hold asks for. Fix: skip the hold when `config.verified.has(name)`. Test first: two verified names at distance 1, both listed.

**[D-7] High | Confirmed | `registry/scripts/src/market-judge.ts:89-110`, `emit.ts:171-175`, `classify.ts:37`, `packages/dsh-plugin-shop/src/client/ShopTab.tsx:890-894`.** `market: true, by: llm` hides an entry from every shelf: only `market: false` names reach `notAShop` in `plugins.json`, and the client hides shop-like names not in it. The verdict is never re-asked and never overwritten. `parseMarketResponse` accepts any name in the batch's `expected` set, so a description in package A that steers the model into emitting `{"name": "<neighbour>", "market": true}` removes a competitor for good; batches are sorted names, so adjacency is chooseable. This contradicts the CLAUDE.md rule that LLM output never removes an entry, and `docs/` has no design record of the market judge or `markets.yml`. The default gateway is `http://8.141.31.123:3000/v1`, plaintext to a bare IP, so an on-path party can both read `LLM_API_KEY` and forge verdicts that get committed. Fix: an LLM `true` becomes a review hold that a human row must confirm before anything is hidden; write the design section; put TLS on the gateway. Test first: a fixture completion naming a neighbour, asserting the neighbour's verdict is not adopted as a hide.

**[B-5 / A-7] Medium | Confirmed | `registry/scripts/src/npm-client.ts:244-245`, `gate.ts:81-83`.** `deprecated: manifest.deprecated !== undefined` reads npm's documented un-deprecation spelling (`npm deprecate <pkg> ""`, which leaves `deprecated: ""`) as deprecated, publishing "Marked deprecated on npm." for a package that is not. The legacy `license: { type, url }` object and `licenses: [...]` array, which npm still publishes with a warning, become "Declares no license." although the author declared one. Fix: `typeof deprecated === 'string' && deprecated !== ''`; read `license.type` and say "license must be an SPDX string" in the detail. Test first: both packument shapes through `toCandidate → gate`.

**[B-8] Medium | Confirmed | `registry/scripts/src/repo-gate.ts:57,115`.** `own.ts` and `github-repo.ts` fold case; the denial lookup and the hold on the GitHub channel do not. `denied someone/dsh-repo-plugin` does not match candidate `Someone/dsh-repo-plugin`; a repo whose manifest name is `DSH-FS-TOOL` sits beside verified `dsh-fs-tool` at distance 9. Fix: lowercase repo full names and hold probes on the GitHub channel. Test first: the two cases above.

**[B-7] Medium | Confirmed | `registry/scripts/src/subpackage-select.ts:17-23,49-88`.** `globToRegex` is anchored only at the start, so nested manifests match `packages/*` and displace real siblings past the 8-cap (`packages/b` and `packages/zeta-plugin` vanish behind `packages/a/lib0…lib6`); explicit non-glob `workspaces` entries are filtered out and the fallback `packages/*` finds nothing; a `**` glob yields no matcher and the convention fallback is skipped. The root then gets the generic `no-bundle` detail, so the author is told to fix the wrong file. Fix: anchor `$`, accept literal paths, support `**`, and extend the detail as the hub-borrowings design requires. Test first: the three tree fixtures above.

**[B-11] Low | Plausible | `registry/scripts/src/repo-gate.ts:77-78`.** A release-rescued repository with `workspace:` deps is rejected with "a git install from outside it cannot succeed", but the entry would install the tarball, whose manifest `pnpm pack` rewrites, so the stated reason may not apply. Reproduce before fixing.

**[B-12] Low | Confirmed | `registry/scripts/src/config.ts:10`, `tier.ts:52`.** `reviewedVersion` is not validated as semver at parse; the build dies in `tier` with `Invalid Version: one-point-two`, not naming `verified.yml`. No parse-time check flags a name present in both `verified.yml` and `denied.yml` (denial wins silently). Fix: validate at load, name the file.

### 4. The network shell under real weather

**[D-1] High | Confirmed | `registry/scripts/src/npm-client.ts:291-306`.** The public registry silently resets any `from > 5000` to page 0 (live: `from=5001` returns the same names as `from=0`; `from=5250&size=250`, the client's 22nd page, returns 250 page-0 objects). The loop never reads `body.total`; at a keyword total of 5,250 or more it receives full duplicate pages, deduplicated by the `Set`, never breaks, and throws at `MAX_SEARCH_PAGES` with "exceeded 100 pages … harvest is broken": the wrong diagnosis, 100 wasted requests, every day until code changes. `keywords:deepseek-harness` is at 5,094 today. The same loop also ends a keyword silently on a short non-final page (249 objects of `total: 600` → page 2 never requested). Fix: read `total`; throw immediately and correctly when `total > 5250`. **Correction (2026-09-03, while writing plan A):** this fix direction was wrong. The live API was probed before the plan was written: adding a `text` term to `keywords:<k>` leaves `total` unchanged and only re-ranks, and so do `scope:`, `author:`, `maintainer:` and the quality weights; `keywords:a,-b` returns 0, so there is no negation; `size=1000` still returns 250. The only filtering dimension is the `keywords:a,b` intersection, and without negation a cell's complement is inexpressible, so **no covering partition exists**. Plan A therefore partitions on intersections and then measures coverage against the keyword's own answered `total`, throwing on a shortfall — safe by check, not by construction. Test first: a fixture registry that wraps past the window, asserting one correctly worded throw and no wasted pages; a fixture with a short non-final page, asserting the next page is requested.

**[D-2 / A-5] High | Confirmed | `registry/scripts/src/npm-client.ts:61-88,340,361-378`, `classify.ts:43-45`.** `fetchWithFailover` rethrows the primary failure when there is no backup or the backup also fails; `fetchCandidate` does not catch it, and `fetchCandidates` uses `Promise.all`, so one ECONNRESET or one 30-second `FetchTimeoutError` on one of ~5,600 packuments rejects the whole harvest with no `fetch-failed` row. The production harvest runs through `classify.ts:43-45`, which passes no backup registry, so the mirror failover from hub-borrowings C is not in the daily path at all. `fetchWithRetry` retries 429 only. CLAUDE.md's "a package that cannot be fetched becomes a `fetch-failed` rejection" holds only for HTTP-status failures. Fix: catch in `fetchCandidate` and return `{ ok: false, detail }` naming the true cause (timeout, network, status); pass the backup or a retry into the classify harvest. Test first: `['good', 'bad']` with `bad` throwing ECONNRESET, asserting one candidate and one `fetch-failed` row.

**[D-3] Medium | Confirmed | `registry/scripts/src/github-client.ts` (`fetchRepoCandidate`, `harvestRepos`).** Any non-ok manifest response becomes `no-manifest` ("No package.json at the repository root"), and `harvestRepos` writes that into `repo-state.json` as a deterministic failure re-fetched only when `pushed_at` changes. A 503, 403 or 451 from raw.githubusercontent.com is therefore recorded permanently with a false reason; the committed state holds 1,918 such records and none can be told apart. Inversely, a repo that deletes its `package.json` keeps its stale candidate listed forever while the same run reports it `no-manifest`. Fix: only 404 is `no-manifest`; everything else is `fetch-failed`; record the failure for previously-recorded repos too. Test first: raw → 503, asserting `fetch-failed` and no state write.

**[D-4] Medium | Confirmed | `registry/scripts/src/github-client.ts:279`.** A window's paging stops on `metas.length < 100` after `parseRepoMeta` has filtered, and `incomplete_results` is never read. One item with a non-string `default_branch` ends the window at 99 of 150; `incomplete_results: true` with a 40-item page yields 40 of 900. Dropped repos become `repo-gone` ("deleted, renamed, or private", wrong), leave the state, vanish from the catalog for a day and re-consume the budget as new tomorrow. Fix: test raw `items.length`, honour `incomplete_results`, reconcile against the probe total. Test first: the two fixtures above.

**[D-5] Medium | Confirmed | `registry/scripts/src/github-client.ts:44-58`, `llm-client.ts:148,155`, `github-stars.ts:44-48`, `.github/workflows/daily.yml` (no `timeout-minutes` on the build job).** Only npm-client passes an `AbortSignal`. Against a socket that accepts and never writes, npm-client rejected after 2 s; github-client was still pending at 8 s. The only bound is undici's default 300 s headers timeout, after which `fetchRobust` retries three times, so a stalled GitHub or gateway ends in the six-hour Actions kill with no report and no state commit. Fix: reuse `withTimeout` in all three modules and add `timeout-minutes` to the build job. Test first: the hung-socket test for each client.

**[D-6] Medium | Confirmed | `registry/scripts/src/npm-client.ts:79-86`, `build.ts:50-51`.** The npm token is forwarded to the third-party backup registry (`registry.npmmirror.com auth=Bearer npm_…` recorded by the fixture), and `NPM_BACKUP_REGISTRY` may be any URL. The documented disable value, an empty string, is not the guard's `undefined`, so `''` produces `registryUrl('', 'x') === '/x'` and `Failed to parse URL` on the first primary failure. A paged search failing over mid-pagination would also mix two indexes with different orderings. Fix: send the token to `REGISTRY` only; treat `''` as disabled; never fail over a paged search. Test first: the fixture asserting no `Authorization` header reaches the backup.

**[D-9] Low | Confirmed | `registry/scripts/src/npm-client.ts:301`.** `searchByKeywords` calls `response.json()` uncaught; a 200 with a non-JSON body dies with a bare `SyntaxError` naming no keyword. Observed once live: page 13 of `keywords:dsh-plugin` returned `<!doctype html>`. There is also no body-size cap on packument or search JSON, unlike the tarball reader. Fix: catch and name the keyword; cap the body.

**[D-10] Medium | Confirmed | `registry/scripts/src/github-client.ts` (`readManifest`'s callers, the systematic-failure bound).** Introduced by the fix for D-5/A-3's sibling, not present before it. Narrowing `no-manifest` to a genuine 404 means every other non-ok status now throws, and the systematic-failure bound turns a pool-wide throw into a failed build. ## The plan

The order below is by what it costs to wait, not by section. Each package names the failing tests to write first (they are the reproductions above, turned into assertions), the fix, and how it ships. Registry-side changes ship on the next daily build and need no package release; anything that changes what the host reads or does goes through `beta` first, per CLAUDE.md.

Two habits carry through every package. First, reproduce before fixing: every *Plausible* item gets its script run before a line of production code changes, and a reproduction that fails to reproduce closes the item with a note. Second, mutation-check every new test the way audit H did: copy the module to `/tmp`, inject the bug the test claims to catch, point the test at the copy, and watch it fail. A test that stays green under its own mutation is not a test.

## Reproduction playbook

Everything here runs without the network and without touching a real profile. The pipeline is a pure function, so a fixture reproduces any policy decision; the host half has a fake-`dsh` seam; the client's logic modules (`present.ts`, `locales.ts`) are plain TypeScript.

**Run a pipeline module directly.** Node 22 strips types in place, so a throwaway script can import the sources without a build:

```sh
node --experimental-strip-types /tmp/repro.ts
# /tmp/repro.ts:
#   import { gate } from '/abs/path/registry/scripts/src/gate.ts'
```

Imports must carry the `.ts` extension and be absolute or relative to the script, not to the cwd — ESM resolves from the importing file.

**Drive the whole pure pipeline from a fixture.** `pipeline.test.ts` shows the shape: build the candidate list in memory, call the pure entry point with an explicit `now`, and assert on the returned artifacts. To test determinism, call it twice with a different `now` and a shuffled input and `Buffer.compare` every artifact — data, stars sidecar, index, badge, report, manifest — not one of them.

**Point the network clients at a local server.** Every client takes its base URL from a parameter or an env variable (check the constructor). A `node:http` server that returns a fixed body, a 429 with `Retry-After`, or accepts and never answers, reproduces the three failure classes that matter. A server that never answers is the timeout test; if the call returns, there is a timeout, and the returned error tells you how it is classified.

**Exercise the host without dsh.** The executor spawns whatever `dsh-cli.ts` resolves. Put a shell script named `dsh` first on `PATH` (or point the resolver at it) that prints canned output and exits with the code you want; that is how the CRLF and failure-line-picker tests work. For a process-tree test, have the fake spawn `sleep 1000 &` and check whether the grandchild survives a kill.

**Probe a live profile without installing anything.** Create an isolated profile with `DSH_HOME=/tmp/probe-home`, install the shop from a tarball made with `npm pack` (pnpm reuses a cached directory for `file:` paths, so a rebuilt directory is not re-read; a tarball is), and insert a throwaway plugin with `--patch` to read runtime truth rather than inferring it. The two entry-id spaces bite here: `cordis.patch.yml` targets bare config ids, while the loader and inventory report `include:<id>`; mixing them no-ops silently.

**Craft a hostile tarball.** `tar` will happily create entries the extractor must refuse:

```sh
cd /tmp/evil && printf x > payload
tar --transform 's|payload|../../escaped|' -cf traversal.tgz payload           # path traversal
ln -s /etc/passwd link && tar -cf symlink.tgz link                              # symlink entry
truncate -s 10G sparse && tar -S -czf bomb.tgz sparse                           # size bomb, small on disk
```

**Test the compatibility check against a modern package.** In a temp `node_modules`, create `x/package.json` with `"exports": { ".": "./index.js" }` and no `./package.json` subpath, then run the real presence check against it. If it reports the package missing, the check is confusing "not exported" with "not installed".

**Windows without Windows.** Two things reproduce on Linux: CRLF (`printf '%b' 'a\r\nb\r\n'` into the fake `dsh`) and the `.cmd` shim rule (read the `spawn` call: if `file` can ever be a shim path, it is broken on Node ≥ 20.12 without `shell: true`). Path separators need a Windows runner; that is what CI's matrix is for if one is added.

**Before claiming anything is fixed.** `pnpm test`, `pnpm typecheck`, `pnpm -C packages/dsh-plugin-shop test`, `pnpm -C packages/dsh-plugin-shop typecheck`, then `rm -rf packages/dsh-plugin-shop/lib && pnpm -C packages/dsh-plugin-shop build` before `npm pack` — `test` and `typecheck --noEmit` both skip `lib/`, and a pack from a stale `lib/` ships old code with a new version number.

## Checked and clean

These hypotheses were tested and hold, so nobody needs to re-audit them next month. The list is deliberately specific.

- **Purity.** No `Date`, `Math.random`, `process`, `fs`, `fetch`, `Intl`, `toLocale*`, `localeCompare` or `env` in the ten pure registry modules; `build.ts` reads the clock exactly once, after the harvest. Every sort in the registry is code-unit; a child `node` under `TZ=Pacific/Kiritimati LANG=tr_TR.UTF-8` produced byte-identical digests for all six artifacts.
- **Hash and integrity.** The bytes hashed are the bytes written; live `sha256sum` of the downloaded data and stars files match the pointer; the host verifies sha256 on the fetched bytes for both files, on the wire and in the cache, and treats a tampered cache as absent. `builtAt` in the hash is caught by three tests.
- **Untrusted input, registry side.** Zod `strict()` rejects unknown keys with an accurate path; `__proto__` is ignored, never propagated; JSON emit round-trips lone surrogates and U+2028; scoped names are single-encoded and both URL forms return 200; no registry code builds a file path from a package name; every regex applied to hostile text (`isShopLike`, `EXCLUDED_DIRS`, `globToRegex`, `hasWorkspaceDeps`, `githubOwnerName`) runs under 4 ms on 100 KB adversarial input; `markets.yml` and `repo-state.json` are JSON-escaped.
- **Untrusted input, host side.** No `dangerouslySetInnerHTML` or `style` props; `href` only for `https?://` repository values and grammar-checked npm names; every `target="_blank"` carries `rel="noopener noreferrer"`; category and tier reach CSS only through closed enums; JSON over the wire neutralises `__proto__`. The i18n interpolation uses a function replacer, so `$'`, `$&`, `$1` and `$$` in module names render verbatim, and the 86 keys have identical placeholder sets in both languages.
- **Process spawning.** The Windows route is `spawn(process.execPath, [bin.js, …])`, never the `.cmd` shim, with no shell anywhere in the shop's own spawns; the leading-`-` operand guard is load-bearing and present; installs are serialised per profile; the restart helper passes argv through `"$@"`. `tar.ts` writes nothing to disk, so traversal, symlink, hardlink and device entries are inert, and `..` or absolute names throw; integrity is verified before gunzip; the tarball host must equal the registry origin. `npmrc.ts` reads only the unscoped `registry=` and never parses, returns or logs a token. `profile.ts` writes temp-then-rename.
- **Secrets and hosts.** Every token travels in env, none on argv; no thrown message or stderr line carries a URL or header; `Authorization` is stripped on cross-origin redirect (tested locally); every fetched host is hard-coded and no packument-supplied URL is ever fetched, so there is no SSRF surface from npm data; the working tree contains no token-shaped string.
- **Policy edge cases.** All gate and tier fixture arithmetic recomputed and correct; a transposition costs 2 and is still held at threshold 2; candidates never hold each other, so a squatter cannot delist an unverified package; denial is checked before the hold; `denied.yml` requires a reason and throws on duplicates; LLM categories are validated against the enum before any write and a failed classification is re-asked; `runBatches` swallows LLM outages without throwing.
- **Config loading (yaml 2.9).** Duplicate keys throw; aliases produce a caught duplicate row; merge keys are not merged under YAML 1.2; a 9⁹ alias bomb throws in 4 ms; `reviewedVersion: 1.10` becomes a loud "expected string, received number", never a silent `1.1`; `yes`/`no` stay strings; empty, comment-only, tab-indented, list-for-map and multi-document files all throw.
- **CI.** No `pull_request_target`; fork PRs see no secrets; deploy, publish and commit steps are guarded by event and branch; `--frozen-lockfile`; Node pinned inside the engines range; a `concurrency` group serialises bot runs; a build failure stops the job before upload. `publish-catalog.ts` uses `${NODE_AUTH_TOKEN}` expansion, provenance, and refuses a same-day version collision loudly. The lockfile has no `git+` or `http` sources.
- **Tests.** 334 + 490 green, both typechecks clean, nothing tracked written; no `vi.mock`, `.only` or `.skip`; fake timers restored; the README-pin and schema-freshness guards fail under every mutation tried; self-update ordering points a beta tester at the stable build and never the reverse.
