# Catalog schema

English | [中文](schema.zh.md)

A plugin is listed by declaring a harvest keyword — `dsh-plugin` or `deepseek-harness` — in its `package.json`. A plugin that never publishes to npm is listed from its GitHub repository instead: add the `dsh-plugin` or `deepseek-harness` *topic* to the repo, keep a `package.json` at the root with a `name` and a `dsh.bundle` section, and the catalog pins the default-branch commit as its version. The `dsh.catalog` section below is **optional**: declare it to control your own listing text, category, and capabilities, or omit it and the catalog derives a listing from what npm already knows. The machine-readable schema for a declared section is [`registry/schema/plugin-entry.schema.json`](../registry/schema/plugin-entry.schema.json), generated from the validator the build runs, so it cannot drift from what is enforced.

```json
{
  "keywords": ["dsh-plugin"],
  "dsh": {
    "bundle":  { "patch": "./cordis.patch.yml" },
    "catalog": {
      "category": "tool",
      "summary": { "en": "Does a thing", "zh": "做一件事" },
      "capabilities": ["fs", "shell"]
    }
  }
}
```

If you declare `dsh.catalog`, both languages are required — declaring the section means declaring both:

| Field | Required | Meaning |
|---|---|---|
| `category` | yes | One of `tool`, `provider`, `ui`, `workflow`, `integration`, `theme`, `other` |
| `summary.en` | yes | One line, 1–200 characters. Not synthesized: a missing translation stays missing |
| `summary.zh` | yes | The same, in Chinese |
| `capabilities` | yes | Up to 20 free-form strings, 1–64 characters each, naming the dsh services the plugin uses |

If you do not declare `category`, the shop may assign one by automated review; declare it to stay in control. The `theme` category is for plugins that change the interface's appearance: skins, themes, visual styles (皮肤、主题、外观).

If your repository is on GitHub, its star count is shown automatically — there is nothing to declare; repositories on other hosts show none.

**`capabilities` is self-declared and unenforced.** dsh does not sandbox plugins, so this field describes what the author says the plugin touches. It is displayed, never checked. Do not read it as a permission grant.

**Every field that reaches the published catalog is length-bounded.** A declared section is copied verbatim into a file every reader downloads, so a value past its bound is rejected with the field named rather than published: `summary.en` and `summary.zh` at 200 characters each, every `capabilities` item at 64. The build bounds the npm manifest fields it reads on your behalf the same way — `name` at 214 characters, `version` at 128, `dist.integrity` at 256, the publication time npm reports at 64, the publishing account at 128, `license` at 128 (past that it is not an SPDX identifier) and `repository` at 512 — and, on both channels, it records at most 128 required `peerDependencies` names, each at most 128 characters. Optional peers are left out before that cap applies, so they never take a slot. Peers past either of those two bounds are dropped from your entry and the listing still appears: that trim is silent and gets no row in the build report. `dsh.compatibility` is bounded the same way — its `dsh` range at 256 characters, each profile name at 64, and at most 16 profiles — and whatever is past a bound is dropped just as silently, with no row. `dist.unpackedSize` — the figure behind an npm package's size on the shelf — is read the same way and kept only when npm reports it as a safe non-negative integer; anything else is dropped and your entry lists without a size, which is also silent and also gets no row. A zero is kept, not dropped: npm reports 0 for an empty tarball and the shelf shows "0 B". A listing taken from a GitHub repository needs its root `package.json` to decode to at most 1 MB (1,048,576 bytes) — the bound is on the decoded JSON measured in bytes, and the build stops reading once it is crossed — and a `name` in the shop's own bundle-name grammar, which is npm's minus the lowercase rule: an optional `@scope/`, then a letter or a digit, then any of letters, digits, `.`, `-` and `_`, at most 214 characters in total. Uppercase is accepted here even though npm forbids it in a new publication — a repository is not an npm publication, and `DSH-FS-TOOL` installs fine — but a leading `.` or `_` is not, in the name or in the scope. A subpackage's directory path is bounded at 200 characters, because it becomes that entry's own identifier (`owner/repo#path`): a longer one is not listed, and its row says the path was cut.

**The size on your card is measured, and how depends on where you list from.** The shelf shows what installing the plugin puts on disk; it reaches the published catalog as `installSize`, which is the key to look for if you are reading `plugins.json` directly. For an npm package that is npm's own `dist.unpackedSize`, so the card and your npm page agree. For a listing taken from a GitHub repository it is the sum of the file sizes in the git tree at the pinned commit — scoped to your subpackage directory when your entry has one, so a monorepo is never charged whole. Directories and submodules contribute nothing: a submodule's content is not in that tree and a tarball install does not fetch it either. It is **not** the size GitHub reports for the repository, which counts history and is not what you install.

Expect a repository figure to run larger than the same code's npm figure. That is real content rather than error: a repository holds the tests, docs and screenshots your npm `files` whitelist leaves out, and a repo install genuinely puts all of it on disk.

A size is a decoration, so failing to measure one costs the label and never the listing, and none of these get a row in the build report. Yours will be absent if npm reported no `dist.unpackedSize` (publishes older than npm 5.6) or reported one that is not a safe non-negative integer; or, on the GitHub side, if the tree came back truncated, any element of it was unreadable, a file reported a size that is negative or not a safe integer, the running sum passed 2^53, or no file matched at all — an empty tree, or a subpackage directory matching nothing. That last one is deliberate: zero files counted is not the same statement as zero bytes, and publishing "0 B" would claim your plugin costs nothing to install.

**One entry also has a total size budget, and it is a different kind of rule.** A field bound says what one value may look like; the budget says what a whole entry may cost. Everything the build takes from you — your `dsh.catalog` section, the manifest fields above, the peers that survived the trim, your `dsh.compatibility` declaration, and the unpacked size if npm reported one — is serialized exactly as it will appear in `plugins.json`, and the result must come to at most **12,288 bytes (12 KiB), counted in UTF-8 bytes** rather than characters: a Chinese summary costs three bytes per character there. The budget is checked last, and on GitHub listings as well as npm ones. Unlike the peer trim it refuses rather than shortens — an entry past it is not listed at all, and its Detail names the byte count it reached and the budget it crossed. So if your package is missing from the catalog entirely, look for its row in the build report; if the entry is there and only some peer names are absent, that was the trim — or you marked those peers optional. The two rules are deliberately not jointly satisfiable at their limits — 128 peers of 128 characters each is far past 12,288 bytes and is refused — so read the budget as the real ceiling and the field bounds as the shape each part may take. For scale: the largest entry today's catalog could hold, every maximum observed on 2026-09-04 gathered into one entry, measures 6,294 bytes, so nothing listed is near it.

The build report lists each rejection as a **Reason** and a **Detail** — read the Detail. Some Reason codes are broader than the case they carry: a `license` or `repository` past its bound reports `no-license` or `no-repository`, and `no-manifest` covers every way a `package.json` we did read cannot be listed — refused for its size, over-bounded in a field, past the entry budget, or carrying a name the bundle-name grammar rejects — so the code can say "no" about something you did declare. The Detail is the accurate half and names the bound you crossed. The converse is worth knowing when you are chasing a listing that never appeared: `no-manifest` means we read your `package.json`, or got a 404 asking for it. If our own request failed instead, the row says `fetch-failed`, and that is retried on the next build rather than held against your repository.

**When a listed package leaves the catalog, the report says why.** Each build compares its harvest with the catalog it last published. If your npm package was listed and the harvest no longer returns it, npm is asked about it once. A package whose latest version still lists `dsh-plugin` or `deepseek-harness` and is not deprecated stays listed. Otherwise the report carries one row on that build: `deprecated`, quoting your deprecation message (up to 200 characters), or `npm-gone`, which says whether the package was unpublished, is no longer on the registry (npm answers 404), lost both keywords, or npm did not answer when asked why — that last case names the failure, and the row is one build's finding rather than a verdict on your package. Add a keyword back and the next build lists it again. (Design 2026-09-26-market-borrowings §8.2.)

**A listing taken from a GitHub repository installs the pinned commit as it is.** No build runs on a git install, so every file your bundle loads must be in the repository at that commit: each `dsh.bundle.patch` file, and the file your `exports` (or `main`) resolves to for each module the patch inserts from your own package. A `lib/` or `dist/` your `.gitignore` excludes is not there, and such a listing is refused as `requires-build` with the missing file named. Commit the built files, publish the package to npm, or, for a repository root, attach a packed release tarball (`npm pack` from a built checkout) to your latest release. A monorepo subpackage cannot be rescued by a release. (Design 2026-09-26-market-borrowings §9.3 and §9.6.)

**A version string or integrity that would break the snapshot's lock line is refused.** The daily snapshot writes one line per listed package into `manifest.lock`, and that file is read back by later builds, so a `version` holding whitespace or a control character, or a `dist.integrity` that is not a list of SRI hashes (`algorithm-base64`, space-separated), would make its line unparseable. The package is refused and the Detail says which of the two it was; publish with a plain version and the integrity npm assigns. (This is the `no-manifest` / `no-integrity` grammar case of the rules above.)

**The same grammar holds a GitHub listing's identity.** A GitHub entry's `owner/slug`, bundle name, and pinned commit or tag are written byte-for-byte into committed artifacts — the github line of `manifest.lock`, the build report — with no length cap, so any of them holding whitespace or a control character is refused. Publish under a name and tag that are plain text. (Same defense as the SRI rule on the npm line.) (Reason: `no-manifest`.)

Unknown fields are rejected rather than ignored, so a typo fails the build with a message naming the field instead of silently dropping your data. That message is itself capped at 200 characters and ends with `… (truncated)` when it was cut; the field name comes first, so the part you need to act on always survives. **A `dsh.catalog` section that fails validation is rejected outright** — it never falls back to a derived listing, because an author who declared the section and got it wrong deserves the build report to say so, not a silent substitute.

## Listed without a `dsh.catalog`

Omit the section entirely and your package is still listed, from your npm `package.json`'s own `description` field:

| Field | Declared | Derived (no `dsh.catalog`) |
|---|---|---|
| `metadata` | `declared` | `derived` |
| `summary.en` | your text | your npm `description`, trimmed and capped at 200 characters |
| `summary.zh` | your text | absent |
| `category` | your choice | `other` |
| `capabilities` | your list (up to 20 items, 64 characters each) | empty |

A package with no `dsh.catalog` and no npm `description` is not listed at all — there is nothing to show. A derived listing carries `metadata: "derived"` in the published entry; adding a `dsh.catalog` section is how you claim it. The shop no longer badges derived entries visually.

`metadata` is independent of trust tier: a derived listing can still be `verified`, because review reads the plugin's code, not its prose.

## Listed, but it does not install or load

Being listed means the build read your manifest and found nothing it refuses. The build never installs your plugin and never runs it, so a listed plugin can still fail on a reader's machine. Below is what dsh 0.2.0-rc.2 — npm's `latest` for `@deepseek-ai/dsh` on 2026-10-13 — does in each case, read from its source, and what you can change.

**Your harness peers leave out the reader's dsh.** dsh checks every `peerDependencies` entry named `@deepseek-ai/dsh` or `@deepseek-ai/dsh-*`, optional ones included, against the version it is running, and a range that leaves that version out refuses the install: before pnpm runs when dsh can read your manifest from the registry, and otherwise after pnpm, restoring the profile's `package.json` and lockfile. A plugin installed before the reader upgraded dsh stays installed and is skipped at startup. The reader can accept the risk for one exact version with `dsh plugin allow-version`; the `dshPeers` paragraph below says when the shop makes this check before the click and shows that command. Prereleases count as the `dsh.compatibility` paragraph below describes, and a caret range on a `0.x` version stops below the next minor: `^0.1.0-rc.6` admits nothing from `0.2.0-0` on and refuses dsh 0.2.0-rc.2. Unlike `dsh.compatibility`, a range dsh cannot parse is refused, not left unjudged. Only `workspace:^`, `workspace:~` and `workspace:*` are read as the running version, so every dsh refuses `workspace:^0.1.0`, a range `npm publish` ships as written. Declare the range of dsh versions you have run your plugin on, and publish with `pnpm publish`, which rewrites `workspace:` ranges.

**A package your patch inserts is checked the same way.** After pnpm, dsh also reads each package your `dsh.bundle.patch` inserts and checks that package's harness peers, and one refusal refuses the whole install. The shop judges only your own manifest before the click, so a refusal for one of these packages comes after pnpm has run. Insert only packages whose harness peers admit the dsh versions you declare.

**`dsh.bundle.patch` must be a file path or a list of file paths, and every file it names must be in what installs.** A missing `patch` or any other value (`true`, a number, an object, a list holding a non-string), or a named file that is not there, stops dsh reading your package: an install is refused with `Cannot validate installed package`, which no exemption clears, and a package that is already installed is skipped at startup, with a `skipping profile bundle` line naming the reason.

**The catalog never opens an npm tarball.** It lists an npm package from the registry's metadata alone, so a file left out of what you publish is found only by the reader's install: a missing patch file is refused as above, and a module your patch inserts that is not there fails when dsh starts it. Before you publish, run `npm pack --dry-run` and check that its list holds every file your `dsh.bundle.patch` names and the file your `exports` (or `main`) resolves to for each module the patch inserts. A GitHub listing is held to this at the gate instead (`requires-build`, above).

**An error during activation is recorded against your entry; an error left unhandled stops dsh.** An error your entry throws, or a promise it rejects, while dsh activates it is recorded against that entry: dsh starts the rest of the profile without it, apart from the plugins that wait for a service it provides, and prints `warning: N entries did not activate`, naming your entry's id, its package and the error. An unhandled rejection or an uncaught exception at any other moment, during startup or long after it — a callback that throws, an `error` event with no listener, a rejected promise nothing handles — ends the whole process: dsh prints `dsh: fatal load failure` or `dsh: fatal uncaught exception` with the error and exits with status 1. dsh also fails to start, printing `startup failed: N required plugins did not activate`, when an entry it requires does not activate — a fixed list of built-in ids, such as `connection` and `webserver` — and a required entry left waiting for a service counts: `connection` waits for the `credentials` service, so a failed credentials provider stops dsh starting, and so does the failure of any plugin that provides a service a required entry waits for. Handle every error your code can raise once activation has returned.

**Under pnpm 11, an install that needs a build script fails.** dsh installs with whichever pnpm the reader has. pnpm 11 runs no package's build scripts unless the profile allows them, and by default (`strictDepBuilds`) a held script stops the install with `ERR_PNPM_IGNORED_BUILDS`, naming the package, which dsh classifies as `build-blocked`. That covers your own `preinstall`, `install` and `postinstall` and every dependency's. The reader has to allow those scripts — pnpm's message points to `pnpm approve-builds`, run in the profile directory — and install again. Publish built code instead of building it on install.

**The version the catalog lists has to stay installable until the next build.** The catalog re-reads your package every day, and the shop installs exactly the version it lists, so unpublishing that version leaves the shop asking npm for a version it no longer has. Deprecate it, or publish a fixed version, instead.

**One profile holds one package of each name.** A profile records one dependency per name, so a fork that keeps the original's `name` can never be installed beside it: `dsh plugin add` replaces whichever of the two is installed, and the shop refuses the install, naming the package that holds the name, until the reader uninstalls it. Give a fork its own `name`.

**Try your plugin the way a reader installs it.** In a throwaway dsh home, add it with the spec the shop uses, then start dsh and read what it prints:

```sh
export DSH_HOME="$(mktemp -d)"
dsh plugin --profile web add <spec>
dsh --profile web --no-open --port 0
```

Then open the address it prints. `--port 0` takes a free port: on the default one, a dsh you already run makes this one fail to start, because `webserver` is a required entry. `<spec>` is `name@version` for an npm package, `github:owner/repo#<commit>` for a GitHub listing (with `&path:<dir>` appended for a subpackage), and the release asset's URL for a listing that installs from a release tarball. Run it on each dsh version you declare, and on npm's `latest` for `@deepseek-ai/dsh`.

## The published catalog data file

Each build publishes the catalog as a content-addressed data file, `plugins.<sha256>.json`, named by the hash of its own contents. Besides the accepted `plugins` array, it carries a `denied` array: every denylisted package with the author-readable reason it was blocked. The Host consults `denied` when a `shop/installStart` request names a blocked package. Rejections that are not denials — a missing bundle, a `dsh.catalog` that failed validation, a name too similar to an existing plugin — appear only in the build report, never in the published data.

Every entry carries `added`, the date it first appeared in the catalog (YYYY-MM-DD) — recorded per package name by the registry, never declared by the author. A GitHub entry rescued from a build script (`requires-build`) installs from a prebuilt release tarball instead of git: it carries an optional `tarball` object (`url` + `sha256`), its `version` is the release tag, and its `integrity` is the tarball's sha256. For such an entry, a `verified` review pins `reviewedSha256` — the reviewed tarball's content hash, never the tag: a tag is a mutable ref that can be re-created on different content, and verified trust must name what the entry actually installs. A `denied` row may carry `replacement`, the name of a legitimate substitute when a human recorded one.

Every entry, npm or GitHub, also carries `peers` — the names of its **required** `peerDependencies`, never a version range, and no field at all when it requires none. A peer you mark `optional: true` in `peerDependenciesMeta` is not recorded, so it never produces a warning. A GitHub listing's peers are read now but published only once the shop release that checks them the way described next is the current one — an older shop would misjudge them — and each repository gains the field at its next re-read: a one-time re-read, spread over several daily builds rather than done in one. A reader's own dsh checks each name against its installation and against the modules its web client provides itself, and warns only about a name neither provides, so the shop can badge a listing before someone installs a plugin their harness cannot run. Shop versions up to 0.8.3 check the installation alone, and so can warn about a module the web client provides itself — `react`, for one; that warning goes away when the reader updates the shop. This required-peer check is a warning, never a refusal: the card still offers Install.

Entries also carry `dshPeers`: your peers on the harness itself, `@deepseek-ai/dsh` and every `@deepseek-ai/dsh-*`, each with the range you wrote, optional ones included, because dsh reads them all. A GitHub entry carries it together with `manifestVersion`, the `version` in the `package.json` that installs, because dsh names an exemption by that version rather than by the commit or tag the catalog pins; an entry whose manifest names no usable version carries neither. Each repository gains both at its next re-read, spread over several daily builds. From dsh 0.1.7, dsh itself refuses an install whose harness peers its running version does not satisfy, unless the reader has exempted that exact version. From dsh 0.1.7, a shop newer than 0.8.3 runs that same check on an npm entry before the click, and a shop from 0.8.7 on a GitHub entry too, by its `manifestVersion`: shops 0.8.4 to 0.8.6 disable Install, and from 0.8.7 a red label stands in its place. Either way the card shows dsh's own exemption command, which the reader can run to accept the risk.

If your manifest declares `dsh.compatibility`, the catalog records that as well: `dsh`, a semver range naming the dsh versions you support, and `profiles`, the dsh profile templates you support — the names dsh itself ships, which on 0.1.5 are `web`, `acp`, `headless`, `sdk` and `sdk-minimal`. Both are optional and either may stand alone; a half that is malformed is dropped without costing the other. The build copies them and never judges them — the reader's own dsh compares them against the version and profile it is actually running, and when either does not match, the shop warns and names both sides: what you declared, and what the reader is running. For a GitHub entry that installs from a release tarball, what is compared is the `package.json` inside that tarball, never the one on your default branch — and its `peers` are read from that same file. A profile you name is met in either of two ways: the reader's profile has that name, or it is built from that template's bundles, whatever it is called — so `web` is met by a profile named `web`, and by any other profile built from the web bundles. A name that is not one of the templates the reader's dsh ships is met only by a profile of exactly that name; otherwise it cannot be judged, so a list that includes one never produces a warning about profiles. Prerelease versions count, so `>=0.1.0` accepts `0.1.5-rc.3`, but a range is read exactly as semver reads it, and a prerelease sorts below its own release. So a floor excludes its own prereleases: `>=0.1.5` and `^0.1.5` both refuse `0.1.5-rc.3`, and `>=0.1.5-0` or `^0.1.5-0` is how you include every `0.1.5-rc.N`. An upper bound you write out does the opposite and admits the next line's prereleases: `<0.2.0` accepts `0.2.0-rc.1`, so write `<0.2.0-0` to stop before them, as `^0.1.0` and `~0.1.0` already do. A range dsh cannot parse is left unjudged rather than guessed at. It is a warning, never a refusal, and declaring nothing is not a claim of incompatibility: it produces no warning at all.
