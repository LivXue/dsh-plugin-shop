# Fork Flag Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Record `forked?: boolean` on github entries, mirroring the C5 archived channel end-to-end (GraphQL `isFork` → `repo-state.json` → emit `forked?: true` → report line), plus fix the wrong comment at `github-stars.ts:185` as its own commit.

**Architecture:** The fork bit rides the *same* GraphQL pass that already fetches `isArchived` (no new requests); it is persisted beside `archived` in the repo state, layered onto candidates, and emitted only as `forked?: true`. Everything is report-only — no badge, no gate change, no scanner.

**Tech Stack:** TypeScript ESM strict, vitest, zod (shop schema), GraphQL via `fetch`.

**Spec:** `docs/design/2026-10-11-fork-flag.md`

## Global Constraints

- Pure core (`types.ts`, `repo-state.ts`, `emit.ts`, `tier.ts`, `pipeline.ts`, `gate.ts`): no clock, no network, no filesystem, no locale. `.strict()` NOT used on the shared zod entry schema — new optional fields parse on old clients.
- `forked?: true` is emitted; `forked: false` is the field's *omission* (mirror `archived`). A "no fact supplied ⇒ no write" rule applies throughout.
- Report line is EXACTLY: `github fork flags: N answered (M forked), K skipped` (three-part; `K skipped` suffix only when `skipped.length > 0`). Printed **conditionally** like the archived note (inside the fetch branch in build.ts) — it does NOT always print; the unconditional `github entries from archived repositories: N` report-*file* line is NOT mirrored (design §1.1 adds no such line for fork).
- `REPO_FIELDS` constant shared by stars + archived + repo-gone: widen ONCE to include `isFork`, update its comment to say *forks + archived persist* while stars/repo-gone read a summary (github-release-assets §1.3 fairness).
- `.ts` extensions in local relative imports; `noUncheckedIndexedAccess` guarded; one trailing newline per file.
- No UI badge, no `verified.yml`/`denied.yml` change, no dedicated scanner workflow.

## Review Focus

1. **Renamed/transferred/deleted repo between search and GraphQL batch** — the `parseRepoMeta` null/undefined arm must leave that repo *without* a fork fact and add it to `skipped` (never write a default).
2. **`isFork` present but non-boolean** — GraphQL type contract is `Boolean`; a non-boolean (e.g. schema drift) must be a skip with reason `"no answer"`, not a cast.
3. **`REPO_FIELDS_REGEX` guard** — the existing test asset strings that pin the shared field list will fail the moment `isFork` is added; the plan names the file to update in the same commit so the guard keeps guarding.
4. **Old `repo-state.json` without `forked`** — `parseRepoState` must accept absence (the field is optional) and `serializeRepoState` must not synthesize `forked: false`.
5. **Shop consumer declaration (R4 rule)** — adding `forked` to the catalog entry type without the consumer line in `packages/dsh-plugin-shop/src/host/catalog.ts` fails `catalog-parity.test.ts`; the plan ships the consumer line in the same PR.
