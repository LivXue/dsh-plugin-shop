# Fork flags recorded like archived — design

Status: **chosen.** Borrowing from the competitor scan of 2026-10-11
(`docs/plans/2026-10-11-competitor-scan.md`); it is never the evidence — every
claim rests on this repository. The 2bingling `decay-scanner` checks four
"decay kinds" — `vanished`, `archived`, `forked`, `stale` — and treats them
as one report. Our daily build already covers three of them:

| decay kind | us | who covers it |
|---|---|---|
| **vanished** | covered | `repo-gone` rule: a repository the index stops serving departs under `repo-gone` (github-client.ts §"departures") and can return on a fresh answer. |
| **archived** | covered | C5 (archived-flag-and-shadowed-recovery §1.3, merged #81 2026-10-08): GraphQL `isArchived` bulk, per-day, report-only, persisted `archived?: boolean`, catalog emit `archived?: true`. |
| **stale** | covered | The GitHub search windows by `pushedAt`, so a repository that stops pushing simply falls out of the harvest window; it stays listed until it namespaces-collides or vanishes — which is what decay means here. |
| **forked** | **the hole** | Nobody reads the fork bit. |

Forked is the only one of the kinds that touches install wiring: a forked
repository is the sharpest early marker that an install may need its `repo`
pointer refreshed. That fact can be obtained for free — **the GraphQL `isFork`
scalar sits beside the `isArchived` the build already fetches** — and the
discipline for reading it was settled on 2026-10-08 (C5): advisory, batched,
"no fact supplied ⇒ no write".

> **The wrong comment this design fixes first.** `github-stars.ts:185` says
> "The GitHub REST search does not carry `archived` on its items (the probe
> proved this)". That is not true; the REST search returns both `archived`
> and `fork`. The probe built 2026-10-08 disproved the *assumption* that
> the REST projection *feeds* the emit, but the field itself has always
> been there. A comment that sells a fact as false is worse than none —
> it stops the next maintainer from asking "why did we not use the REST
> item?". The first commit of this change replaces the comment, by itself.

## 1. Fork flags: persisted, layered, emitted, reported

### 1.1 The rule

Add `forked?: boolean` to the repository record in `repo-state.json`. Read it
from GraphQL `isFork`, batched 200 per call beside `isArchived`. Persist it
with exactly the same "answered ⇒ write, skipped ⇒ no write" discipline as
archived. Layer it onto the run's candidates so the emit can read it. Emit
`forked?: true` on each github entry whose repo-state record holds
`forked: true` (omitted otherwise; additive). The build report gains one line:

```
github fork flags: N answered (M forked), K skipped
```

`forked: false` is `forked`'s omission — we do not emit it, just as archived
is emitted only on true. The flag is informative: it does not change the
gate, the verified/denied path, or the shelf.

### 1.2 Why this and not a scanner

2bingling runs a dedicated cron (`decay-scan.yml`) because their architecture
is a static snapshot that the harvest never regenerates; decay must be
re-discovered on a schedule. Our daily build regenerates the whole catalog
every day: a forked repository that must leave the catalog leaves it through
`repo-gone` (its namespace vanished) or through the gate (its declarations
changed), not through decay. The fork bit is *not* a removal criterion; it is
reporting telemetry. A dedicated workflow would run the same build and
produce the same line — the channel, not the cadence, is the deposit.

### 1.3 The mechanism (mirror of C5 §1.3)

- **Fetch**: extend the per-build pass over listed github repositories to
  query `isFork` on the same aliases as `isArchived`. The batched count is
  unchanged; the GraphQL alias literal `{ isArchived isFork }` sits inline
  beside the existing `isArchived` (this design was drafted against a
  `REPO_FIELDS` constant that the implementation never extracted — there is
  no such constant in the source tree). If a shared constant is extracted
  later, a regex-pin guard test should replace the inline form.
- **Persist**: `applyForkFlags` writes to `repo-state.json`. It is a separate
  function, not a rolls-into-archived one, mirroring the discipline that the
  two kinds decay independently.
- **Emit**: `plugins.<sha>.json` gains `forked?: true` on github entries
  whose repo-state record holds `forked: true`. `layerForkFlags` is the emit
  side's projection, mirroring `layerArchivedFlags`.
- **Report**: the line quoted above, on the build report. The line names the
  fact and its magnitude; it does not interpret — a forked repository could
  be a stale mirror, an active fork, or a typo the gate stopped earlier, and
  the number is all the diagnostic needs.

## 2. `?? stats`: JSON-pointer projection over live READMEs (second commit)

### 2.1 The gap

The catalog records `name`, `version`, `stars` — but not *how many installs
a plugin has seen this week*, *its download rank inside its own category*, or
*how close the harness is to its stated `peerDependencies`*. Those three
numbers live upstream in the repositories' READMEs and in the national
download mirrors, and they are the substrate of every "top in its category"
claim a marketplace makes.

### 2.2 The rule

Introduce a **`?? stats`** structure on the catalog entry, and a harness-side
`statsProjection` that reads it:

```ts
export const STATS_SCHEMA_VERSION = '2026-10-11.1'

export interface RepoStats {
  /** Weekly download count, from the repository's own metadata. */
  weekly?: number
  /** Rank inside the plugin's own primary category, 1-based. */
  categoryRank?: number
  /** Current dsh version vs the plugin's stated peer range, for the harness. */
  peerHealth?: 'ok' | 'stale' | 'mismatch' | 'unknown'
}
```

The projection itself is a **JSON-pointer read over the published catalog**
(with the `archived` and `forked` already inside it): the harness reads the
`?? stats` node, applies the weekly/category-rank/peer-health lens, and
emits a recomputed `stats` block onto plugins.json. This is a projection —
the catalog does not carry the weekly number; the stats projection computes
it and writes it back.

The motivation is the competitor's weekly-rank pages and the shop's own
weakest card: with `?? stats` an `outdated` github entry can ask "is my
category rank still 3, or has it dropped past the visible top-10?" and the
same arithmetic the report uses for stars is reusable for downloads.

### 2.3 Not built

- **A downloader inside the registry.** The projection reads READMEs and
  mirrors; the harvest itself is unchanged.
- **A forked UI badge.** The fork is reported only; a `已归档 / Archived`
  precedent exists (C5), but no fork badge ships today.
- **A new schema field in `index.json`.** The stats goes on the catalog
  entries, inside the per-plugin blob, and is not on the pointer.

## 3. Testing

- **Fork**: one fixture batch answering `{ isFork: true, isArchived: false }`
  lives in a new `applyForkFlags` fixture; a second batch answering
  `{ isArchived: true, isFork: false }` lives in the existing
  `applyArchivedFlags` fixture to confirm the two kinds are recorded
  independently.
- **Stats**: the projection is a pure function; the e2e reads its summary on
  the catalog-instance fixture (no network). The peer-health lens reads live
  README data, which does not ship to the catalog UI; the same lens RFC is
  a separate design.

## 4. Order

Two commits, on one branch:

1. `feat(registry): record github entries' fork flag and rename the shared repo-fields constant` — the fork field, the repo-fields widening, the apply + layer functions, the report line.
2. `feat(registry): lay the stats substrate with one stats projection` — `RepoStats`, `statsProjection`. Both in registry only.

Any top-level UI work that would succeed the stats projection is a separate
design.
