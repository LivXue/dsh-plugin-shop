# dsh 0.2.2-rc.2: the same harness, plus git-update methods

**Date:** 2026-11-12
**Status:** accepted
**Changes:** the CI matrix's 0.2.2 leg, and the e2e contract header

dsh `0.2.2-rc.2` was published on 2026-11-12 at 02:16 UTC, under npm's
`next` tag. npm's `latest` is still `0.2.2-rc.1`, published 2026-11-04 — so
a plain `npm i @deepseek-ai/dsh` still installs rc.1, and this change does not
move what a reader gets. It moves what the suite is measured against.

The question this document answers is narrow and factual: **does the shop
work against rc.2, and did anything it depends on move?** Everything below was
measured against two installed harnesses, `0.2.2-rc.1` and `0.2.2-rc.2`, side
by side.

---

## 1. What changed in the harness

The two releases are the same line. `dsh`'s manifest names 89 shared
dependencies: 81 of them move from `0.2.2-rc.1` to `0.2.2-rc.2`, and the
other 8 are the `cordis` packages, whose `~` ranges are unchanged.

One dependency leaves and one arrives:

| | |
|---|---|
| gone | `@deepseek-ai/dsh-experimental-agent-team-profile` |
| new | `@deepseek-ai/dsh-cua-bundle` |

Neither is a harness service the shop reads. `peerDependencies` and
`optionalDependencies` are **identical** between the two releases.

## 2. What the shop reads, and whether it moved

The shop's host half reads four packages out of a running dsh. Their export
surfaces, compared by importing both installs:

| package | rc.1 | rc.2 | |
|---|---|---|---|
| `dsh-app-boot` | 57 exports | 57 exports | same names |
| `dsh-official-bundles` | 12 exports | 12 exports | same names |
| `dsh-home-paths` | 16 exports | 16 exports | same names |
| `dsh-plugin-manager` | 4 exports | 5 exports | **plus** `pinnedGitOrigin` |

The `PluginManager` class itself goes from 36 methods to 39, and **none is
removed or renamed**. The three that arrive are `planGitUpdate`,
`checkRegistryUpdate` and `gitHostUnreachable` — all about updating a plugin
from a git origin, which is the feature this release carries. The shop calls
six manager methods — `installBundle`, `removeBundle`, `updateBundle`,
`setBundleEnabled`, `setPluginEnabled`, `cancelInstall` — and all six are
present in rc.2 unchanged.

The shop's own harness peers are `>=0.1.1-rc.2 <0.3.0-0`, which admits
rc.2 on dsh's own rule (`repo-guards.test.ts` checks this against the
matrix, so the matrix and the manifest cannot drift apart).

## 3. The profile table did not move again

`0.2.2-rc.1` moved `PROFILE_TEMPLATES` out of `dsh-app-boot` into
`@deepseek-ai/dsh-official-bundles`, and the shop's `dsh.compatibility.profiles`
verdict went silent until it started reading it there (design
`2026-11-06-dsh-022-profile-templates.md` §1). That was the last breaking
change to a harness surface this shop touches, so it is the one worth
re-measuring.

Both releases export the table from `dsh-official-bundles`, with the same five
templates and the same keys:

```
acp, headless, sdk, sdk-minimal, web
```

Identical. The badge still fires.

## 4. The e2e, run against rc.2

The matrix's rule is that a version is listed only after the e2e has been RUN
against it, so it was run before this change, on both exit criteria, with
`DSH_SHOP_EXPECT_DSH=0.2.2-rc.2` so that a `dsh` answering any other
`--version` fails the run instead of making it vacuous:

| | |
|---|---|
| `web-full-flow.e2e.ts` (P2) | **12 / 12 pass** |
| `real-install.test.ts` (P1) | **3 / 3 pass** |

Every version branch in the e2e is a `gte()` threshold — `0.1.7-rc.1`,
`0.1.7-rc.2`, `0.2.1-rc.1` — and none of them compares a patch number, so
rc.2 takes the same branch rc.1 took.

## 5. What this does not mean

- **It does not move what users install.** `latest` is still `0.2.2-rc.1`.
  The matrix leg is a measurement, not a distribution.
- **It does not retire rc.1 from the world.** rc.1 is still `latest`, and a
  reader on it runs the shop against it. The matrix now measures rc.2 because
  the two are the same harness to this shop — §2 and §3 — and a leg is a
  harness BEHAVIOUR, not every patch of it. If rc.1 needs its own leg
  alongside rc.2, that is one more axis value and two more jobs.
- **It says nothing about the git-update methods.** They are new surface, and
  the shop does not call them. Whether the shop should — `planGitUpdate` and
  `checkRegistryUpdate` look like the answer to a question the shop has been
  asked before, but that is a design question and not this one.

## 6. What changed in this repository

- `.github/workflows/plugin.yml`: the `dsh` matrix axis, `0.2.2-rc.1` →
  `0.2.2-rc.2`, and the comment that records which harness each leg is.
- `packages/dsh-plugin-shop/tests/client/web-full-flow.e2e.ts`: the contract
  header, which `repo-guards.test.ts` holds equal to that axis.
- `docs/plans/2026-08-18-remaining-work.md`: item 13, the running record of
  harness versions.
